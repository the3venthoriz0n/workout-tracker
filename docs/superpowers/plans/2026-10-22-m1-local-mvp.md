# M1 Local MVP (Guest Mode) Implementation Plan

> **Status: Done (2026-10-26). M1 shipped; the checkboxes below were not ticked as work went, so they are not a progress record. Later changes (restyle, angles, AMRAP, supersets, layered rules, day colours) live in the spec.**

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A guest-mode workout tracker that runs entirely in the browser: gear, exercise library, plans with overrides and progression rules, one-tap set logging, automatic progression, history, units and export.

**Architecture:** Pure domain logic (schemas, effective values, progression, units, seeds) lives in `packages/shared` with unit tests. `apps/web` talks to a `Repo` interface through TanStack Query hooks. M1's only implementation is `LocalRepo` on Dexie (IndexedDB). The API is not touched in M1.

**Tech Stack:** React 19.3, Vite 8, React Router 8.5, TanStack Query 5.104, Dexie 4.4, Tailwind 4.3 + shadcn/ui (CLI 4.22), lucide-react, zod 4.6, Vitest 5 + happy-dom + fake-indexeddb + Testing Library.

**Spec:** `docs/spec.md` (sections 5–8 are the contract for this plan).

## Global Constraints

- All commands run through `just` (Docker). Node and pnpm are never run on the host. Run one package's tests with `just pnpm --filter <pkg> exec vitest run <file>`.
- Pin exact dependency versions (no `^`/`~`), as the scaffold does. New versions: `dexie@4.4.6`, `@tanstack/react-query@5.104.5`, `react-router@8.5.0`, `tailwindcss@4.3.3`, `@tailwindcss/vite@4.3.3`, `lucide-react@1.61.0`, `fake-indexeddb@6.2.6`, `happy-dom@21.0.4`, `@testing-library/react@16.3.3`, `@testing-library/user-event@14.6.8`, `shadcn@4.22.1` (CLI, run with `dlx`, not installed).
- React Router 8 is newer than the plan author's reference material. Check its docs for the SPA/declarative router API before Task 8.
- IDs come from `crypto.randomUUID()`. Timestamps are ISO strings. Every user-owned record has `user_id`, `created_at`, `updated_at`, `deleted_at` (spec §5).
- Deletes are soft (set `deleted_at`); every list/get filters out soft-deleted rows.
- Effective values: `targetX = item.target_x ?? item.x ?? exercise.default_x` (spec §6). Editing an item's `reps` or `weight` override clears `target_reps`, `target_weight` and `fail_streak`.
- Default progression rule: `add_weight` by `profile.weight_increment`, `fail_streak_limit: 3`, `deload_pct: 10`, `rep_ceiling: null`.
- Default increments: `lb: 5`, `kg: 2.5`.
- `video_url` must be `http:` or `https:` (it is rendered as a link).
- UX: tap targets ≥ 44 px; weight inputs use `inputmode="decimal"`, rep inputs `inputmode="numeric"`; at most one sheet/dialog open; light and dark mode.
- Public repo: no personal data, IPs or secrets in code, fixtures or commits.
- Commit after each task on branch `ak/scaffold` (Conventional Commit messages, ending with the repo's Co-Authored-By line).

## Review Focus

1. **Blank override input**: clearing the reps/weight field on a plan item must store `null` (fall back to the exercise default), never `0`. Test in Task 6.
2. **Decimal weight entry**: `"62.5"`, `"62,5"` and `" 62.5 "` parse to `62.5`; `""` means "no value"; `"abc"` and negatives are rejected and the previous value is kept. Test in Task 1 (`parseWeight`).
3. **Plan edited mid-session**: deleting a plan item, day or plan while a session for it is in progress must not break finishing it. History keeps the snapshotted names, and progression skips the deleted items. Test in Task 7.
4. **App closed mid-workout**: reloading returns to the in-progress session with its done sets intact, and a second session can't be started. Test in Task 7.
5. **Unit switch**: lb→kg converts exercise defaults, item overrides and targets, and set-log weights, rounded to 0.1 (135 lb → 61.2 kg), and resets the increment to 2.5. Test in Task 7.

### Task 3: Progression engine

**Files:** Create `packages/shared/src/progression.ts`, `packages/shared/test/progression.test.ts`

**Interfaces:**

- Produces:
  - `type Outcome = 'skipped' | 'success' | 'miss' | 'deload'`
  - `progress(input: { targetReps: number; targetWeight: number; baseReps: number; plannedSets: number }, rule: RuleInput | null, failStreak: number, sets: Pick<SetLog, 'done'|'actual_reps'|'weight'>[], increment: number): { targetReps: number; targetWeight: number; failStreak: number; outcome: Outcome }`

Algorithm: spec §6, steps 1–6, verbatim. "Done sets" are those with `done: true`. Success needs `doneSets.length >= plannedSets` and every done set with `actual_reps >= targetReps && weight >= targetWeight`.

### Task 7: LocalRepo sessions, finishing, history, units, export

**Files:** Modify `apps/web/src/repo/local-repo.ts`; create `apps/web/test/local-repo.sessions.test.ts`

**Interfaces:** Consumes `progress`, `convertWeight`, `DEFAULT_INCREMENT` (Tasks 1–3); implements the remaining `Repo` methods plus `updateProfile`.

Behavior:
- `startSession` creates one `set_log` per planned set (`effective.sets`) for each live item, with `target_reps`/`target_weight` from `effective`, `actual_reps = targetReps`, `weight = targetWeight`, `done: false`. It snapshots `plan_name`, `day_name` and `exercise_name`.
- `finishSession` runs in one Dexie transaction:
  - For each `plan_item_id` that still exists (not soft-deleted), call `progress` and write the item's `target_reps`, `target_weight` and `item_state`.
  - Set `completed_at`.
